> **What you'll learn.** How to write your first end-to-end test with Playwright — the testing tool that drives real browsers (Chromium, Firefox, WebKit) the same way a user would.

## Why E2E (and why Playwright)

Unit tests and component tests catch bugs in isolated units. **End-to-end** tests catch bugs in the *seams* — the place where your code, the network, the browser, and the user actually meet. They're the tests that ask "if a real user did this, would it work?"

Playwright is the modern leader because:

- It drives Chromium, Firefox, and WebKit from one API.
- It auto-waits for elements to be ready — no `sleep(500)` flake.
- The tooling — codegen, trace viewer, debugger — is genuinely good.
- It speaks the modern web (Shadow DOM, iframes, web workers) without ceremony.

## Install

In any Node project (or `pnpm init` a new one):

```bash
pnpm dlx create-playwright@latest
```

The wizard installs `@playwright/test`, downloads the browser binaries (~250MB), and scaffolds a `playwright.config.ts` plus an example test. Press Enter to accept defaults.

Run the example:

```bash
pnpm exec playwright test
```

You should see three browsers open and close in milliseconds, with a passing test. Welcome to E2E.

## Anatomy of a test

```ts
// tests/example.spec.ts
import { test, expect } from '@playwright/test';

test('homepage has Atlas in the title', async ({ page }) => {
  await page.goto('https://atlas.dev/');

  await expect(page).toHaveTitle(/Atlas/);
});

test('clicking "Start your journey" goes to /start', async ({ page }) => {
  await page.goto('https://atlas.dev/');

  await page.getByRole('link', { name: 'Start your journey' }).click();

  await expect(page).toHaveURL(/\/start\/?$/);
  await expect(page.getByRole('heading', { name: /pick your starting point/i })).toBeVisible();
});
```

A few patterns to internalize:

**`page` is the test fixture.** It's a fresh, isolated browser context per test. No state leaks between tests.

**`getByRole` is the right way to find elements.** It mirrors how assistive tech sees the page. Tests written this way also test your accessibility — if the screen reader can't find it, neither can your test.

**`expect(page).toHaveX()` auto-waits.** Playwright keeps polling until the assertion passes or the timeout (5 seconds by default) trips. You almost never need explicit `waitFor`.

## Codegen — write tests by clicking

The fastest way to start writing tests is to record yourself using the app:

```bash
pnpm exec playwright codegen https://atlas.dev/
```

A browser opens alongside an inspector window. Click around the app — Playwright writes the test for you, picking the most resilient selector for each interaction. Copy what you like into a real test file and tighten the assertions.

<Callout variant="tip" title='Prefer "role" and "label" selectors'>
Codegen will sometimes use CSS selectors. When you can, swap them for `getByRole`, `getByLabel`, or `getByText` — they survive refactors and reflect real user intent. Reserve `data-testid` for cases where there really isn't a semantic anchor.
</Callout>

## Network mocking

Don't hit production APIs in tests. Mock the boundary:

```ts
test('shows fallback when API fails', async ({ page }) => {
  await page.route('**/api/posts', (route) =>
    route.fulfill({ status: 500, body: '{"error":"oops"}' })
  );

  await page.goto('https://atlas.dev/blog/');

  await expect(page.getByText(/couldn\'t load posts/i)).toBeVisible();
});
```

`page.route` intercepts requests matching a glob. You decide whether to fulfill, abort, or modify them. Perfect for testing loading, error, and empty states.

## The trace viewer (the killer feature)

When a test fails in CI, Playwright records a **trace** — a timeline with every action, network request, console log, screenshot, and DOM snapshot.

Open it locally:

```bash
pnpm exec playwright show-trace trace.zip
```

You can scrub through the test like a video, hover any action to see the page state at that moment, and click through the network panel — all in a normal-looking DevTools UI. Most "flaky" tests aren't flaky once you've seen the trace.

## Running in CI

The default `playwright.config.ts` already does the right thing:

```ts
// playwright.config.ts
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './tests',
  retries: process.env.CI ? 2 : 0,
  reporter: process.env.CI ? 'github' : 'list',
  use: {
    baseURL: 'http://localhost:3000',
    trace: 'on-first-retry',
  },
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
    { name: 'firefox',  use: { ...devices['Desktop Firefox'] } },
    { name: 'webkit',   use: { ...devices['Desktop Safari'] } },
  ],
  webServer: {
    command: 'pnpm dev',
    url: 'http://localhost:3000',
    reuseExistingServer: !process.env.CI,
  },
});
```

`webServer` boots your dev server before tests, so CI doesn't need a separate step. `trace: 'on-first-retry'` keeps trace files small in green runs but gives you the full picture when something fails.
