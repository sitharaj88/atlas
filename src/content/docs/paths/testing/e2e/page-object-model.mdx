## What it is

Encapsulate page-specific logic in a class:

```ts
export class LoginPage {
  constructor(private page: Page) {}
  async goto() { await this.page.goto('/login'); }
  async login(email: string, password: string) {
    await this.page.getByLabel('Email').fill(email);
    await this.page.getByLabel('Password').fill(password);
    await this.page.getByRole('button', { name: 'Sign in' }).click();
  }
}
```

```ts
test('login', async ({ page }) => {
  const login = new LoginPage(page);
  await login.goto();
  await login.login('a@b.com', 'pw');
  await expect(page).toHaveURL('/dashboard');
});
```

## When POM helps

- Many tests share the same flows (login, navigation, complex forms).
- A team where a few people maintain test infrastructure.

## When POM is overkill

- A handful of tests with unique flows.
- Simple apps where the page methods are barely more than the inline calls.

A "fixtures" approach (`test.extend({ login: ...async... })`) often beats classes for Playwright specifically.
