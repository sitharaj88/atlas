## Sessions

Server stores a session record. Client holds an opaque session ID (in an HTTP-only cookie). Each request, server looks up the session.

Pros: revocable instantly. Small token. Server controls lifecycle.

Cons: needs server-side storage (Redis, DB).

## JWTs

A signed, self-contained token with claims (`sub`, `exp`, etc.). Client stores it; server verifies the signature without lookup.

Pros: stateless. Microservice-friendly. Works across services that share a secret/key.

Cons: revocation is hard (blocklist or short TTL + refresh). Larger token. If the secret leaks, all tokens compromise.

## The default should be sessions

For 95% of apps, sessions in HTTP-only cookies are simpler, safer, and more flexible. Reach for JWTs when you have:

- Microservices that need to validate tokens without a shared session store.
- Mobile clients that can't share cookies cleanly.
- Federated identity (OAuth/OIDC tokens are JWTs by spec).

## A safe cookie

```text
Set-Cookie: sid=abc123;
  HttpOnly;          (JS can't read — defends XSS)
  Secure;            (HTTPS only)
  SameSite=Lax;      (CSRF defense)
  Path=/;
  Max-Age=2592000;   (30 days)
```
