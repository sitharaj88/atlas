> **What you'll learn.** Why media queries fall short for modern component-driven UIs, and how container queries let a component style itself based on the **space it has**, not the **device it's running on**.

## The problem with media queries

A media query asks: *"how big is the **viewport**?"* That was fine when pages had one column. But components live everywhere — sidebars, modals, dashboards — and a "card" component doesn't know whether its container is 200px wide or 800px wide. With media queries, the same component looks identical at every nesting level, even when the design clearly calls for it to adapt.

Container queries flip the question to: *"how big is the **container** I'm sitting in?"*

## The two-step setup

You declare a **container** on the parent, then write a query that looks at it from any descendant.

```css
/* 1. Mark the parent as a container */
.card-grid {
  container-type: inline-size;
  container-name: cards;
}

/* 2. Style descendants based on the container's size */
@container cards (min-width: 32rem) {
  .card { display: grid; grid-template-columns: 8rem 1fr; }
}

@container cards (min-width: 48rem) {
  .card { grid-template-columns: 12rem 1fr 8rem; }
}
```

`container-type: inline-size` tells the browser to track the container's width (the inline axis in horizontal writing modes). You can also use `size` to track both axes — though it has bigger layout implications.

`container-name` is optional but recommended; it lets you address a specific container when components are nested.

## The mental shift

```diff
- "How big is the viewport?"        ← media queries
+ "How big is the container?"       ← container queries
```

Once you internalize this, you stop thinking about pages as "mobile" or "desktop" and start thinking about components as **resizable** — they should look right at any size. That mental shift makes design systems vastly cleaner.

## Container query units

Inside a container query block, you can use units that resolve relative to the container, not the viewport:

| Unit | Meaning |
|---|---|
| `cqi` | 1% of the container's inline size |
| `cqb` | 1% of the container's block size |
| `cqw` / `cqh` | width / height (alias) |
| `cqmin` / `cqmax` | smaller / larger of inline and block |

Useful for fluid type *inside* a component:

```css
@container cards (min-width: 24rem) {
  .card h3 { font-size: clamp(1rem, 4cqi, 1.5rem); }
}
```

## Common pitfalls

<Callout variant="warn" title="`container-type: size` triggers strict containment">
With `inline-size`, only the inline axis is contained. With `size`, both axes are — which means the container collapses to its minimum height unless you give it one explicitly. Prefer `inline-size` unless you really need height-based queries.
</Callout>

- **Forgetting to set `container-type` on the parent.** Containers are opt-in. No `container-type`, no queries fire.
- **Querying the wrong container.** When containers are nested, `@container` matches the **nearest ancestor with `container-type` set**. Use `container-name` to be explicit.
- **Treating `container` like a layout primitive.** It's a contextual selector, not a layout method. Containers don't add display, padding, or margin — they just become *queryable*.

## Browser support

As of 2026, container queries (size and style) are supported in all evergreen browsers. You can use them safely in production. For very old browsers, your design just falls back to the unconditional baseline — which should look fine at "card sits in a single column."
