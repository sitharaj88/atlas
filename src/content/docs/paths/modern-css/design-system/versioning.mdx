> **What you'll learn.** How to ship a design system as a package without breaking the apps that consume it.

## SemVer rules of thumb

- **Patch (1.2.X)** — bug fixes, no API changes.
- **Minor (1.X.0)** — new features, no breaking changes.
- **Major (X.0.0)** — breaking changes (renamed/removed component or prop, changed default behavior).

For design systems specifically, **visual changes** are tricky. A subtle padding adjustment isn't breaking by SemVer, but it can cause layout regressions in apps. Document major visual changes as breaking, even if the API is unchanged.

## Changesets — the workflow

```bash
pnpm dlx changeset init
pnpm changeset      # describe the change, pick severity
git commit -am 'add changeset'
```

On merge, a bot opens a PR that bumps versions and updates a CHANGELOG. Merge → publish.

Several apps, one monorepo? Changesets handles that too — version each package independently.

## Consuming versioned tokens

Apps pin a version:

```json
{ "dependencies": { "@my/design-system": "^2.4.0" } }
```

Major-version upgrades require a coordinated PR. Patch and minor are safe.

## Deprecation playbook

When removing a component:

1. **Mark deprecated** in JSDoc / TS deprecation tag — TS warns at usage sites.
2. **Add a console.warn** in dev (not prod).
3. **Wait at least one minor release** — give consumers time to migrate.
4. **Provide a codemod** — a script that rewrites consumers' imports.
5. **Remove in the next major.**

## Themes and tokens

Token changes are spookier than component changes — every app picks them up automatically. Treat changes to **semantic** tokens like API changes; **primitives** can adjust more freely if semantics stay stable.

<Callout variant="tip" title="Visual regression catches what SemVer misses">
A visual-regression test harness (Chromatic, Percy, or Playwright + screenshot diffs) catches "the padding shifted 2px" before consumers do. The single most-valuable safety net for a design system.
</Callout>
