> **What you'll learn.** Why TypeScript happily accepts a `Point2D` where you asked for a `Vec2` — and the cases where that's surprising.

## Structural typing

TS compares types by their **shape**, not their **name**:

```ts
type Point  = { x: number; y: number };
type Vec2   = { x: number; y: number };

const p: Point = { x: 1, y: 2 };
const v: Vec2 = p; // ✓ same shape, different name — fine
```

Languages like Java/C# use **nominal** typing — same shape, different name = different type. TypeScript doesn't care about the name, only the shape.

## Excess properties

When you assign a literal directly, TS adds an **excess property check**:

```ts
type User = { id: number; name: string };
const u: User = { id: 1, name: 'Ada', extra: 5 }; // ✗ excess
```

Excess property checks only fire on **fresh object literals**. Assign through a variable and they relax:

```ts
const data = { id: 1, name: 'Ada', extra: 5 };
const u: User = data; // ✓ no fresh-literal check
```

## The "branding" workaround

When you genuinely need nominal types (USD vs. EUR money), brand them:

```ts
type USD = number & { __brand: 'USD' };
type EUR = number & { __brand: 'EUR' };

function payInUSD(amount: USD) {}
const x = 10 as USD;
const y = 10 as EUR;
payInUSD(x); // ✓
payInUSD(y); // ✗ Argument of type 'EUR' not assignable to 'USD'
```

The `__brand` is fictional — it never exists at runtime. But TS treats `USD` and `EUR` as distinct because the brand differs.

## Wider vs. narrower

A type `A` is assignable to `B` if `A` has **at least** the properties `B` requires:

```ts
type A = { x: number; y: number; z: number };
type B = { x: number; y: number };
const a: A = { x: 1, y: 2, z: 3 };
const b: B = a; // ✓ A has everything B needs
```

Going the other way fails — `B` doesn't have `z`.

<Callout variant="tip" title="When name-based mistakes bite">
Two types with the same shape are interchangeable. If a `RawId` and a `UserId` are both `string`, TS won\'t catch a mix-up. Brand them when correctness matters.
</Callout>
