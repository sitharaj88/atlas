> **What you'll learn.** Four built-in combinators, when each is right, and how to stop hammering an API by accidentally doing 1,000 things at once.

## The four combinators

```js
// All must succeed; rejects fast if any reject
Promise.all([p1, p2, p3])
  .then(([r1, r2, r3]) => /* ... */);

// Resolves with array of {status: 'fulfilled', value} or {status: 'rejected', reason}
Promise.allSettled([p1, p2, p3])
  .then(results => results.forEach(r => /* ... */));

// First to settle wins (success OR failure)
Promise.race([p1, p2, p3]);

// First to FULFILL wins; rejects only if all reject (with AggregateError)
Promise.any([p1, p2, p3]);
```

| Use case | Combinator |
|---|---|
| Need every result; one failure = total failure | `all` |
| Need every result, even partial | `allSettled` |
| Implement a timeout: race fetch against `setTimeout(reject, ...)` | `race` |
| Fastest of N redundant providers | `any` |

## Race for timeouts

```js
function timeout(ms) {
  return new Promise((_, reject) =>
    setTimeout(() => reject(new Error(`timed out after ${ms}ms`)), ms)
  );
}

const data = await Promise.race([
  fetch('/api').then(r => r.json()),
  timeout(5000),
]);
```

Modern alternative: `AbortSignal.timeout(5000)` for fetch:

```js
const res = await fetch('/api', { signal: AbortSignal.timeout(5000) });
```

## Limited concurrency

Calling `Promise.all` on 10,000 items launches 10,000 simultaneous fetches. The server hates you, your browser cries.

Limit with a small pool:

```js
async function pMap(items, mapFn, concurrency = 5) {
  const out = [];
  let i = 0;
  async function worker() {
    while (i < items.length) {
      const idx = i++;
      out[idx] = await mapFn(items[idx]);
    }
  }
  await Promise.all(Array.from({ length: concurrency }, worker));
  return out;
}

const results = await pMap(urls, fetchJson, 5);
```

Libraries like **`p-limit`** and **`p-map`** do this with one line if you'd rather not roll your own.

## Sequential vs. parallel

```js
// Sequential (slow but safe — preserves order, can short-circuit)
for (const url of urls) {
  await process(url);
}

// Parallel
await Promise.all(urls.map(process));

// Parallel with limit
await pMap(urls, process, 5);
```

When ordering matters or each step depends on the previous, sequential is the right choice.

## Promise.withResolvers — modern ergonomics

Sometimes you need to expose `resolve`/`reject` to the outside:

```js
const { promise, resolve, reject } = Promise.withResolvers();

emitter.once('done', resolve);
emitter.once('error', reject);

return promise;
```

Cleaner than `let resolveOuter; new Promise((r) => resolveOuter = r);`.

## Async iterators

For streams of values:

```js
async function* fetchPages(url) {
  let next = url;
  while (next) {
    const res = await fetch(next).then(r => r.json());
    yield res.items;
    next = res.next;
  }
}

for await (const page of fetchPages('/api/list')) {
  for (const item of page) process(item);
}
```

`for await…of` waits on each yielded Promise before continuing.

<Callout variant="tip" title="Don't await in a loop unless you mean it">
`for (const x of xs) { await fn(x); }` runs sequentially. If the operations are independent, that\'s an easy 10× slowdown. Use `Promise.all(xs.map(fn))` (with a concurrency limit if the list is large).
</Callout>
