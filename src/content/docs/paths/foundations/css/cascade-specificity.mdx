> **What you'll learn.** When two CSS rules try to style the same property, the browser runs an algorithm to pick one. Understand it once and stop wondering "why isn't my style applying?"

## The cascade in four steps

Browser walks through these in order. As soon as one declares a winner, it stops.

1. **Origin and importance** — user agent vs. user vs. author. (Author CSS — yours — is the middle layer; `!important` flips priority within an origin.)
2. **Cascade layers** — `@layer` rules. Later layers beat earlier ones. Unlayered styles win against layered.
3. **Specificity** — how specific the selector is.
4. **Source order** — last declaration wins.

Most fights happen at steps 3 and 4.

## Specificity, the math

Count three numbers, written `[a, b, c]`:

- **a** = inline `style="..."` declarations (only `[1, 0, 0]` or `[0, 0, 0]`)
- **b** = number of IDs (`#thing`)
- **c** = number of classes, attributes, pseudo-classes (`.foo`, `[type="text"]`, `:hover`)
- **d** = number of types and pseudo-elements (`p`, `::before`)

Read left to right; bigger wins. `[0, 1, 0, 0]` beats any number of classes.

| Selector | Specificity |
|---|---|
| `*` | `0,0,0,0` |
| `p` | `0,0,0,1` |
| `.btn` | `0,0,1,0` |
| `p.btn` | `0,0,1,1` |
| `.btn.large` | `0,0,2,0` |
| `#header .btn` | `0,1,1,0` |
| `<style="…">` (inline) | `1,0,0,0` |
| `!important` | beats all the above (within its origin) |

`:not(.x)`, `:is(...)`, `:has(...)` take the specificity of their *most specific* argument. `:where(...)` always has zero specificity — useful for resets.

## A worked example

```html
<a class="link" href="...">Hello</a>
```

```css
.link        { color: orange; }   /* 0,1,0 */
a            { color: blue;   }   /* 0,0,1 */
```

`.link` wins (`0,1,0` > `0,0,1`). The link is orange.

```css
.link        { color: orange; }       /* 0,1,0 */
header a     { color: blue;   }       /* 0,1,1 */
```

`header a` wins. Two factors: a class and a type.

## Cascade layers — the modern escape hatch

Specificity wars used to end with `!important`. Now `@layer` is cleaner:

```css
@layer reset, base, components, utilities;

@layer reset {
  *, *::before, *::after { box-sizing: border-box; }
}
@layer base {
  body { font-family: system-ui; }
}
@layer components {
  .btn { padding: 0.6rem 1rem; background: navy; color: white; }
}
@layer utilities {
  .hidden { display: none; }
}
```

Layers declared later **always** beat earlier ones, regardless of specificity. So a single class in `utilities` beats `#some-id .complex .selector` in `components`. No more `!important`.

Unlayered styles win over all layers — useful for overrides, dangerous if you're not careful.

## When to reach for `!important`

- ❌ "I can't figure out why my style won't apply." → Inspect with DevTools, find the actual winner.
- ❌ "I want my reset to win." → Use `@layer` instead.
- ✅ Utility classes that *must* win (`.hidden { display: none !important; }`) — but `@layer utilities` covers this too.
- ✅ Overriding a third-party stylesheet you don't control.

## Inheritance vs. cascade

Two different things:

- **Cascade** picks which rule applies to *this* element.
- **Inheritance** decides what value to use when no rule applies — most properties inherit from the parent (color, font, line-height); some don't (margin, padding, border, background).

If a child has nothing styling its color, it inherits the parent's. The cascade isn't involved at all.

<Callout variant="tip" title="The DevTools secret weapon">
Open DevTools → Elements → Styles. The browser shows every rule that *could* apply, with strikethroughs on the ones that lost. The winning rules are highlighted. This is the fastest way to debug "why isn\'t my CSS working?"
</Callout>
