## Color contrast

WCAG 2.2 sets minimum contrast ratios for text:

| Level | Normal text | Large text (≥18.66px bold or ≥24px) |
|---|---|---|
| **AA** (legal minimum in most jurisdictions) | 4.5:1 | 3:1 |
| **AAA** | 7:1 | 4.5:1 |

Non-text UI (button borders, form input outlines): **3:1** at AA.

Tools:
- DevTools → Inspector → color picker shows the ratio.
- **Stark** (Figma plugin) for design.
- **WebAIM Contrast Checker** — https://webaim.org/resources/contrastchecker/

## Don't rely on color alone

A red error message paired with green success requires color discrimination. Add an icon, an aria-live region, or a label:

```html
<!-- ❌ Color-only -->
<p style="color: red">Email is invalid</p>

<!-- ✓ Icon + color -->
<p style="color: red"><span aria-hidden="true">⚠</span> Email is invalid</p>

<!-- ✓ Color + aria-live for screen readers -->
<p role="alert" style="color: red">Email is invalid</p>
```

About 8% of men have some form of red/green color-blindness. Designers underrate this constantly.

## Motion and animation

Some users get motion sickness from page animations. Respect their preference:

```css
.menu { transition: transform 200ms; }

@media (prefers-reduced-motion: reduce) {
  .menu { transition: none; }
  /* Or in Atlas's reset: */
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
  }
}
```

```js
const reduce = matchMedia('(prefers-reduced-motion: reduce)').matches;
if (!reduce) playVideo();
```

Don't auto-play videos. Don't have giant scroll animations. Don't have flashing content faster than 3 Hz (epilepsy risk).

## A 5-minute screen reader test

**macOS:** Cmd+F5 turns on VoiceOver.
**Windows:** download NVDA (free).
**iOS:** Settings → Accessibility → VoiceOver.

Now:

1. **Tab through the page.** Does VO announce a clear name and role for each control?
2. **Use VO+H** (macOS) to navigate by heading. Are headings in a logical order? Does the page outline make sense?
3. **Use VO+L** to list links. Are they descriptive ("Read more" everywhere is a fail)?
4. **Submit a form** with errors. Does VO announce the error?
5. **Open a modal.** Does VO move into it?

Five issues found in five minutes is normal on a fresh codebase. Each fix lifts everyone.

## Common screen reader fails

- Buttons named "click here" or "read more" (out of context).
- Empty `<a>` or `<button>` (icon-only without `aria-label`).
- Form inputs without `<label>`.
- Modal opens but focus stays behind.
- Toast notifications with no `aria-live`.
- "+" or "→" as the entire button content.

## Tools that catch automatable issues

- **axe DevTools** browser extension.
- **Lighthouse** Accessibility category.
- **eslint-plugin-jsx-a11y** in JSX projects.
- **Pa11y** for CI scanning.

These catch ~30% of issues. The rest need humans (and screen readers).
